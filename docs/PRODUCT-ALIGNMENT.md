# TestHub 产品方向对齐（2026-10）

基于与 DeepSeek 的产品讨论，TestHub 不追求“把 YAML 做成第二套可视化数据库”，而是：

1. **YAML/DSL 是自动化用例的源真相**；平台负责管理、触发、报告、设备与结构化视图。
2. **平台页面编辑是 YAML 的结构化投影**；只做高频受限编辑，结构性修改回到 YAML/Git/AI。
3. **原子步骤有限而稳定**：HTTP/SQL/Groovy/消息/自定义组件；复杂逻辑走工程组件，不在 DSL 内造通用语言。
4. **变量契约显式化**：步骤级 `extract` 产出、模板读取、未定义变量静态提示。
5. **AI 产出必须可校验**：生成后先跑只校验不执行；AI 驱动 UI 与脚本型 UI 分列，不混算通过率。
6. **Git 同步与调度**是后续层：当前已具备执行引擎/队列/计划；Git webhook、组件契约注册、调度能力注册按阶段补齐。

## 已落地

- 场景 **只读流程图**：步骤树、控制器嵌套、前后置节点、变量读取/产出。
- **结构化编辑**：表单步骤树增删/排序/参数编辑，保存回 YAML；不产生第二套数据模型。
- **变量生产者—消费者分析**与未定义变量静态提示，接口：
  - `POST /api/v1/api-scenarios/analyze`
  - `GET /api/v1/api-scenarios/{id}/graph`
- 流程图只读，YAML 仍是唯一编辑源；不做双向同步。

## 后续优先级

1. 文本用例 ↔ 接口/UI 自动化用例的轻量关联与最近执行状态（不做断言级映射）。
2. API 单步组件的输入/输出变量契约，并在场景静态校验中阻断缺失依赖。
3. Git 作为场景 YAML 的源真相：webhook 同步 + 定时兜底 + 变更 diff。
4. UI 自动化用例类型标记（脚本型/AI 驱动型）与报告分列。
5. UI 知识库控件引用、真机会话与调度能力注册。
6. 场景 YAML 的受限编辑（参数/排序/启停）与 AI Skill 示例/校验闭环。

## 边界

- 不把流程画布变成第二套数据模型；不在 V1 做自由连线和实时双向同步。
- 不把 JMeter 嵌入 TestHub；执行引擎保持稳定，YAML 负责声明。
- 关联不做断言级映射，腐化检测后置为巡检。
